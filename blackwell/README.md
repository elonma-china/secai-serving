# 4× RTX PRO 6000 Blackwell + RTX 5090

## Routing

| Role | GPU | Endpoint | Model |
|---|---|---|---|
| LLM | 4× RTX PRO 6000, two TP2+EP2 engines on pairs 0–1 and 2–3 | `:8005/v1` via nginx | `orcarouter/Qwen3.8-Flash-Next-Uncensored-NVFP4` |
| Embedding, planned | RTX 5090 | `:8000/v1/embeddings` | `DuyTa/sec-embedding` |
| Rerank, planned | RTX 5090 | `:8002/rerank` | `DuyTa/sec-rerank` |
| OCR, planned | RTX 5090, resident vLLM + private adapter | `127.0.0.1:18083/v1/ocr` | `ATH-MaaS/OvisOCR3` |
| Translation | Same LLM engines | `:8005/v1/chat/completions` | OrcaRouter Qwen3.8 |

The target uses **two Vast instances**: one homogeneous four-GPU offer and one
single-5090 offer. The client routes by service URL. The 5090 instance is
currently stopped after a successful HTTP connectivity test; no auxiliary
model has been deployed. Keep OCR on loopback and
reach it through an SSH tunnel, using the separate token generated by
`blackwell/aux.sh`. If an application requires one bearer key for all three
public routes, supply the same serving `API_KEY` to both instances.
The embedding model must remain the one used to build the existing vector
index; changing it requires rebuilding that index.

No rental or instance destruction happens in these scripts. The local Vast
credential at `~/.config/vastai/vast_api_key` is used by the Vast CLI, never
copied into this repository or onto an instance. The Hugging Face token and
the serving bearer key are distinct secrets.

## Prepare Vast instances

The `vllm/vllm-openai:latest` image tested on 2026-11-09 contained vLLM
0.33.0 and **failed to load this OrcaRouter checkpoint**: its fused QKV loader
combined the checkpoint's FP8 Q/K/V weights with a BF16 indexer. The upstream
fix is [vLLM PR #62318](https://github.com/vllm-project/vllm/pull/62318).
The official nightly wheel at commit `85b52c9f5309c2f179b40cafa563de0c2f714922`
loaded the checkpoint and passed an authenticated inference smoke test on the
four-GPU instance. Pin an image or wheel containing that fix; check installed
dependencies before keeping a deployment long term. `transformers>=5.16` is
required by the checkpoint card. The LLM checkpoint is gated: accept its
conditions on Hugging Face and provide an existing `HF_TOKEN` for download.
Plan at least 350 GB disk there for the ~178 GB model,
image, cache and runtime. For PLE-on-CPU measurements, verify enough free
**host RAM and pinned-memory allowance** before loading. The 5090 instance
needs space for the embedding/rerank and OvisOCR3 models;
start with at least 150 GB disk.

Search offers without assuming the GPU name is exactly `RTX_PRO_6000`:

```sh
vastai search offers 'num_gpus=4 gpu_ram>=90 disk_space>=350 rentable=true verified=true' --raw
vastai search offers 'num_gpus=1 gpu_ram>=30 disk_space>=150 rentable=true verified=true' --raw
```

Inspect each result's `gpu_name`, `is_bid`, price, host RAM and location;
the second search must select an **RTX 5090**. Do not substitute a mixed GPU
offer for TP4. On the rented four-GPU host, record:

```sh
nvidia-smi --query-gpu=name,memory.total,power.limit --format=csv
nvidia-smi topo -m
```

The scripts assume Vast's SSH launch mode and a checked-out copy of this
repository on each instance. The LLM role needs `blackwell/llm.sh`; the 5090
role needs `blackwell/aux.sh`, `blackwell/ocr_adapter.py`, and
`templates/qwen3_reranker.jinja`. Supply `API_KEY` and `HF_TOKEN` through a
private secret channel; do not paste their values into on-start scripts or
Git. For the two-replica profile, port-map frontend `8005` on the LLM instance
and `8000`, `8002` on the
5090 instance. Do **not** map `18083` publicly.

```sh
# Four-GPU instance, one process per PCIe pair
PARALLEL_MODE=tp2_ep2 LLM_GPU_IDS=0,1 LLM_PORT=8001 \
  PLE_LOCATION=cpu LOG_DIR=/workspace/logs/replica-a \
  LLM_SPECULATIVE_CONFIG='{"method":"mtp","num_speculative_tokens":2}' \
  API_KEY=... bash blackwell/llm.sh
PARALLEL_MODE=tp2_ep2 LLM_GPU_IDS=2,3 LLM_PORT=8003 \
  PLE_LOCATION=cpu LOG_DIR=/workspace/logs/replica-b \
  LLM_SPECULATIVE_CONFIG='{"method":"mtp","num_speculative_tokens":2}' \
  API_KEY=... bash blackwell/llm.sh
# Install blackwell/nginx-llm-tp2.conf as /etc/nginx/conf.d/blackwell-llm.conf,
# then run nginx -t && nginx.

# Separate 5090 instance; OvisOCR3 defaults to enabled
API_KEY=... bash blackwell/aux.sh
```

`llm.sh` validates the selected two or four RTX PRO 6000 GPUs, prints topology,
then starts vLLM in a detached session, waits for health and runs an
authenticated chat smoke test. `aux.sh` validates exactly one RTX 5090,
starts embedding and rerank, then OvisOCR3 on an internal port. A small
adapter retains the existing `/v1/ocr` request/response shape and uses a
separate private bearer token. Its backend sends the model's `plain_ocr`
task prompt via OpenAI-compatible chat completions. The three resident vLLM
memory shares default to 0.14, 0.14 and 0.30 of the 5090's VRAM; measure
actual load and resize these shares if needed.
The embedding and rerank context limits are 1024 and 2048 tokens, matching
their published training limits.
OvisOCR3 uses the model card's Triton GDN prefill backend and image processor
bounds of 448² to 2880² pixels.
For an embedding/rerank-only 5090 role, use `ENABLE_OCR=0`.

OvisOCR3's model card gives a vLLM 0.22.1 offline example; this profile uses
the current vLLM serving API. The card does not establish that the combined
5090 stack has been tested, so run one authenticated OCR inference and check
the resulting text before routing production traffic. Startup includes a
small synthetic OCR inference smoke. The adapter accepts
the legacy `Qwen/Qwen3-VL-2B-Instruct` request model as an alias for gateway
compatibility, while the backend always runs OvisOCR3. It does not provide
bounding boxes or confidence in the plain OCR mode. Translation requires no
resident MT process: send a constrained translation prompt to the LLM URL.

## LLM configuration and A/B profiles

The initial comparison baseline was `PARALLEL_MODE=tp4_ep4`, `PLE_LOCATION=gpu`, max model length
131072, max 64 sequences, 16384 batched tokens and GPU utilization 0.90.
Quantization and BF16 KV follow the checkpoint; the script does not force
another format. Vision stays available by default; `LLM_LANGUAGE_ONLY=1`
is an explicit text-only option if the workload never sends images.

PLE placement is **always explicit**. Current vLLM recipes say CPU offload
may be enabled by default, so an absent flag cannot serve as the GPU
baseline. For each comparison, restart the engine with only this one change:

```sh
PLE_LOCATION=gpu PARALLEL_MODE=tp4_ep4 bash blackwell/llm.sh --dry-run
PLE_LOCATION=cpu PARALLEL_MODE=tp4_ep4 bash blackwell/llm.sh --dry-run
```

The commands emit `--engram-config '{"cpu_offload":false}'` or `true`.
On the measured Server Edition host, CPU PLE raised KV capacity from 2.86M to
4.66M tokens for TP4+EP4 while the short throughput tests were nearly equal.
The two TP2+EP2 replicas with CPU PLE won the concurrent-load screen. See
[measured results and expert-routing analysis](EXPERT_ROUTING.md).

Run the identical benchmark matrix against each restarted profile:

```sh
export API_KEY=... BASE_URL=http://127.0.0.1:8001
PROFILE=tp4_ep4_ple_gpu bash blackwell/bench.sh --dry-run
PROFILE=tp4_ep4_ple_gpu bash blackwell/bench.sh
# Restart with PLE_LOCATION=cpu, then run PROFILE=tp4_ep4_ple_cpu.
```

It covers 2K/512, 8K/1K, 32K/1K at concurrency 1/8/32 and
126976/2048 at concurrency 1/4/8. The last case fits the 131072-token
limit with margin. Results are separate JSON files under `results/<profile>/`.
Compare TTFT, TPOT/ITL, request throughput and aggregate output tokens/s;
record GPU memory, host RAM, PCIe/NUMA topology and load logs alongside them.
The random benchmark shows capacity and scheduler behavior; repeat the
winning candidates with representative RAG, coding and tool prompts before
selecting a production profile. A subsequent fixed-seed flag screen found
MTP depth 2 raised single-stream decode from 130 to 182 output tok/s and
mixed C8 throughput from 499 to 549 tok/s, at a 27% KV-capacity cost.
Increasing batched tokens to 32768 did not materially improve prefill.
Both live replicas now use fixed MTP depth 2. With fresh-seed random
8K-input/512-output prompts and both GPU pairs loaded together, aggregate
output throughput measured ~891, ~1088, ~1274 and ~1399 tok/s at total
client concurrency 16, 32, 64 and 128. At 256 queued clients it remained
~1398 tok/s while TTFT p99 rose to ~81 s; this is a workload-specific
throughput plateau, not an interactive CCU target. The active scheduler cap
is 64 sequences per replica. Use `blackwell/bench_ccu.sh` to repeat the sweep.
See [the live handoff](HANDOFF.md) for all profile results, instance status,
and measured tail latency. Nsight Systems 2026.5.2 traces now show that
32K prefill GPU kernel time is led by NCCL (~28%), while C1 decode is led
by generic GEMM (~44–45%) and MoE expert compute (~18–19%). MoE router and
dispatch together are ~4–5% of decode kernel time; QSA and GDN each ~3%.
Both traced GPUs were active for 92–94% of the decode kernel span, so a
large CPU scheduling stall was not observed in that request. See the handoff
for methodology and limits. Custom kernel work remains out of scope.

## Application routes

For a future externally mapped deployment, expose nginx `8005` for the LLM
and `8000`/`8002` for the auxiliary role. `blackwell/routes.py` accepts
`--llm-port 8005` when those mappings are available. The current four-GPU
benchmark instance maps SSH only, so its frontend is reachable through an
SSH tunnel. The 5090 has no resident services yet.

```sh
ssh -N -L 127.0.0.1:18005:127.0.0.1:8005 \
  -i ~/.ssh/secai2026 -p <LLM_SSH_PORT> root@<LLM_SSH_HOST>
# The tunneled LLM URL is http://127.0.0.1:18005/v1.
```

For OCR, tunnel the private port from the 5090 instance and give the OCR
client its own bearer token from
`/workspace/secai-ovis-ocr.token` through your secret store. Neither tunnel
nor token belongs in the public route table. Translation uses the LLM route;
there is no separate MT URL.
